# BC-01 Government Integration - status

Complete (code + tests). Dev port 5101. DB `JobPlatform_GovernmentIntegration`, schema `govint`.

## Implemented
- **Domain**: 8 aggregates - the 6 catalogued (`EmployerVerification` AGG-06, `GovernmentVerificationData` AGG-26,
  `EducationalCredentialVerification` AGG-27, `IdentityVerificationData` AGG-28, `LegacyData` AGG-35, `DataQuality` AGG-36) plus the 2
  proposed support aggregates (`MigrationRun`, `GovernmentSourceConnection`), each with its state machine, invariants (rule codes
  `GI.Aggregate.*`) and external error codes from the handover's section 4.1/4.2 catalogue (`E-ERPM-UPSTREAM-TIMEOUT`,
  `E-GDI-UPSTREAM-TIMEOUT`, `E-GDI-FORBIDDEN`, `E-CONSTR-UPSTREAM-TIMEOUT`, `E-DMIG-UPSTREAM-TIMEOUT`, `E-DMIG-INVALID-FIELD`, plus
  `E-GI-*` added for rules the handover names only internally - see deviations). Value objects: `Submission` (extensible via
  `AdditionalFields`), `Subject`, `VerifiedField`, `Credential`, `IdentityClaim`, `LastKnownGood`. Entities: `VerificationAttempt`,
  `MigrationPhase`, `MigrationLogEntry`. Domain service `GovernmentDataAccessPolicy` (US-3.4.2-06, stateless allow-list) and the
  append-only `GovernmentDataAccessLogEntry`. Read replica `KnownAccount` (fed by `AccountCreated`, D-01). All 6 domain events raised
  map 1:1 onto the 6 frozen integration events; repository interfaces per handover section 8.2.
- **Application**: every command/query of handover section 7.1/7.2 except the ones folded into a simpler flow (see deviations) -
  `RequestEmployerVerificationCommand` (runs the automatic MoL check inline), `DecideEmployerVerificationManuallyCommand` (adds
  `Reject`, Q-03), `RequestGovernmentVerificationCommand`/`RequestEducationalCredentialVerificationCommand`/
  `RequestIdentityVerificationCommand` (each authorises via `GovernmentDataAccessPolicy` and logs the decision before touching a
  source), `ConfigureGovernmentSourceConnectionCommand` (idempotent upsert), `RunSourceReconciliationCommand`,
  `StartDataMigrationCommand`/`TestMigrationPhaseCommand`/`RollbackMigrationRunCommand`, `ImportLegacyDataBatchCommand`,
  `CleanseMigratedDataCommand`, `PurgeExpiredGovernmentDataCommand`, `RecordKnownAccountHandler` (inbox for `AccountCreated`).
  Queries: `GetEmployerVerificationQuery` (owner-or-admin), `ListPendingManualReviewQuery`, `GetSubjectVerificationStatusQuery`,
  `ListGovernmentSourceConnectionsQuery`, `GetGovernmentSystemsQuery`, `GetMigrationRunQuery`, `GetDataQualityQuery`,
  `ListGovernmentExchangesQuery`. `GovernmentIntegrationEventMapper` (the 6 domain -> integration event mappings). Anti-corruption
  ports per handover section 4.3: `IMolRegistryClient`, `IPefClient`, `IGovernmentDatabaseClient` (all three implement a shared
  `IGovernmentVerificationSourceClient.CheckSubjectAsync`), `IEducationalInstitutionClient`, `IGovernmentIdClient`,
  `ILegacySourceReader`.
- **Infrastructure**: EF Core `GovernmentIntegrationDbContext` (schema `govint`), JSON-column conversions for `Submission`,
  `VerifiedFields` and `ValidationErrors` (value objects with no identity of their own), owned types for `Subject`, `Credential`,
  `IdentityClaim` and the nullable `LastKnownGood`, child tables for `VerificationAttempt`/`MigrationPhase`/`MigrationLogEntry`,
  unique indexes (`LegacyData` on `SourceSystem+SourceRecordId` for INV-11, `GovernmentSourceConnections` on `Source`), repositories
  for all 10 domain interfaces, `GovernmentIntegrationReadStore`, outbox/inbox wiring, the `AccountCreated` inbox consumer feeding
  `KnownAccounts`. Default adapters for the 6 anti-corruption ports are deterministic stubs (Q-04: no external spec or WireMock
  harness is available in this environment - see deviations).
- **Api**: `/api/v1/employer-verifications` (POST, GET/{id}, GET pending-review, POST {id}/manual-decision),
  `/api/v1/admin/government-connections` (PUT/{source}, GET), `/api/v1/admin/migrations` (POST, POST {id}/rollback, GET/{id}),
  `/api/v1/admin/data-quality/{batchId}` (GET), and the internal surface `/internal/v1/gov-verifications`,
  `/internal/v1/educational-verifications`, `/internal/v1/identity-verifications`, `/internal/v1/verification-status`,
  `/internal/v1/government-systems`, `/internal/v1/government-exchanges` - all per handover section 6.1, with role policies
  (Employer / Administrator / InternalService), `GovernmentIntegrationErrorMessages` (ar+en, one entry per code this service
  returns), `Idempotency-Key` support on `POST /employer-verifications`.

## Assumptions / deviations (resolving handover section 12 open questions)
- **Q-01 (migration destination)**: not resolved here - out of scope for this pass. `LegacyDataImported` is published exactly as
  frozen; no BC-04/05/09 bulk-import consumer was added (that decision belongs to those BCs' owners, per the handover's own framing).
- **Q-02 (verification-outcome consumers)**: implemented the recommended "both" option's synchronous half -
  `GetSubjectVerificationStatusQuery` (`/internal/v1/verification-status`) lets BC-04/05 pull identity/credential/gov-data status on
  demand. The events themselves are already published and BC-04 can add an inbox handler for them independently; this BC does not
  own that change.
- **Q-03 (MoL reviewer / reject path)**: implemented as proposed - the Administrator role plays the MoL reviewer, and
  `RejectManually` adds a `Rejected` terminal state alongside the source's `Verified`.
- **Q-04 (external system specs / WireMock)**: no WireMock harness is available in this sandbox. The 6 anti-corruption ports
  (`IMolRegistryClient`, `IPefClient`, `IGovernmentDatabaseClient`, `IEducationalInstitutionClient`, `IGovernmentIdClient`,
  `ILegacySourceReader`) are fully defined and the domain/application logic around them (retry-exhaustion, escalation, no-match
  semantics) is unit-tested against configurable fakes; the shipped default adapters are deterministic stubs that always report a
  match (or an empty legacy page), sufficient to boot and smoke-test the Api. A real deployment swaps these adapters for
  Polly-wrapped HTTP clients behind the same ports - nothing else in the BC changes.
- **Q-05 (ambiguous identity match)**: implemented as proposed - `IdentityVerificationData.MarkUnverified(AMBIGUOUS)` when the source
  reports more than one candidate; never auto-picks one.
- **Q-06 (connection health event)**: left as the source's own "sync API only" option - `GET /internal/v1/government-systems`
  answers BC-02's F-0001 read; no `ConnectionHealthChanged` event is published.
- **Q-08 (access-decision audit trail)**: not added as a new integration event. Every access decision (allow and deny) is written to
  `GovernmentDataAccessLogEntry` and surfaced to BC-07 via the documented backfill query `GET /internal/v1/government-exchanges`
  (handover section 6.1) instead of a live event, matching the handover's own note that this endpoint is "backfill only; live path is
  events" for the *verification* events - access decisions were never catalogued as an event and adding one was judged out of scope.
- **Automatic verification runs synchronously, not via an enqueued internal command**: the handover's application table describes
  `RequestEmployerVerificationCommand` as enqueuing `RunAutomaticEmployerVerificationCommand` separately. This codebase's building
  blocks provide the outbox/inbox for cross-BC integration events but no generic in-process command queue, so
  `RequestEmployerVerificationHandler` calls the MoL check inline within the same request/transaction. Functionally equivalent for a
  single automatic attempt; a production version could move this to a hosted background command without changing the aggregate or
  its rules.
- **`ResilientSourceClient` (30s timeout / 3 retries, Polly)**: not implemented as a shared Infrastructure component. The retry/
  timeout policy is instead a contract of each port (`SourceCallOutcome.Unavailable` is the final answer after retries) that a real
  adapter is responsible for; the shipped stub adapters have nothing to retry against. No Polly package was added.
- **`INV-02` (account must exist and be Employer)**: enforced by the application handler against the `KnownAccounts` replica before
  the aggregate is constructed, not inside `EmployerVerification.Request` itself - the aggregate has no dependency on account state,
  matching the pattern BC-05 uses for the same replica.
- **Retention purge (US-2.5-03 AC-03)**: `PurgeExpiredGovernmentDataCommand` calls `Purge()` on expired `GovernmentVerificationData`
  (its `VerifiedFields` collection is cleared). `EducationalCredentialVerification`/`IdentityVerificationData` carry one small claim
  rather than a growable encrypted collection; their repositories expose `ListExpiredAsync` for a future pass, but no purge/delete
  is wired for them yet (known limitation, listed again below).
- **Encryption at rest (AES-256, US-2.5-04)**: not implemented at the application/column level in this pass (no SQL Server instance
  in this environment to configure Always Encrypted/TDE against) - consistent with how BC-03/BC-09 documented the same gap. The
  columns that should be encrypted (`SubmissionJson`, `VerifiedFieldsJson`, `IdentityClaim.*`, `SourcePayload`) are flagged in the
  handover's own table (section 8.1) and are ordinary columns here.
- **Mobile number validation**: kept permissive (`^\+?[0-9]{7,15}$`) rather than hard-coding the Palestinian `+970 59x/56x` ranges the
  handover flags as "confirm" - a stricter pattern can be dropped in once confirmed without touching the aggregate.
- Added external error codes not named in the handover's table, in the `E-GI-*` family, for rules the handover names only by their
  internal `GI.Aggregate.RULE` code (e.g. `E-GI-ALREADY-DECIDED`, `E-GI-NOT-IN-MANUAL-REVIEW`, `E-GI-SNAPSHOT-ISOLATION`,
  `E-GI-NOT-FULLY-MAPPED`, `E-GI-MIGRATION-ALREADY-ACTIVE`). All administrator-only refusals across `MigrationRun` and
  `GovernmentSourceConnection` share `E-GI-FORBIDDEN`.
- **Single-run migration guard**: implemented as an application-level check (`IMigrationRunRepository.GetActiveAsync`) rather than
  the handover's proposed Redis lock (`prod:government-integration:migration:lock`) - sufficient for the single-instance SQLite/
  in-memory topology this environment tests against; a multi-instance production deployment should add the Redis lock around the
  same check.

## Verified by running
Domain 49, Application 33, Infrastructure 13, Api 18, Architecture 11 tests green (124 total); `dotnet build` of all four `src`
projects individually: 0 warnings, 0 errors.

**Not executed here (no Docker / SQL Server / RabbitMQ / Redis):** all Infrastructure tests run against SQLite and all Api tests
against the in-memory cache/bus (`Database:Provider=Sqlite`, `Cache:Provider=InMemory`, `Messaging:Provider=InMemory`, per
`appsettings.Development.json`). The SQL Server-specific paths (schema `govint`, real `rowversion`, column encryption) and the real
RabbitMQ outbox/inbox publish/consume path are therefore not verified against real servers, only against their SQLite/in-memory
equivalents. No `[DockerFact]`-tagged tests were written.

## Known limitations
- Legacy migration (`ImportLegacyDataBatchCommand`) uses identity-stub mapping/transformation (the external MoL/PEF schema is
  unknown, Q-04); the stage machine, idempotency and validation-exclusion behaviour are fully exercised, but no real field mapping
  exists yet.
- `EducationalCredentialVerification`/`IdentityVerificationData` retention purge is not wired to a scheduled job (see deviation
  above) - only `GovernmentVerificationData` is purged by `PurgeExpiredGovernmentDataCommand`.
- No `RetentionPurgeJob`/`ExpireDuePostingsJob`-style hosted service was added to call `PurgeExpiredGovernmentDataCommand` or
  `RunSourceReconciliationCommand` on a schedule; both are implemented as on-demand application commands a caller (or a future
  hosted service) can invoke.
- Encryption at rest and the Palestinian mobile-number range are not implemented (see deviations).
- The solution-wide `dotnet build`/`dotnet test` was intentionally not run, per this task's constraints (other agents build sibling
  BCs concurrently); only this BC's 4 `src` projects and 5 `tests` projects were built/tested, individually, and are green.
