# BC-06 Help Content - status

Complete (code + tests). Dev port 5106. DB `JobPlatform_HelpContent`, schema `content`. No EF migration was generated (every other BC's
`Infrastructure/Persistence/Migrations` folder is produced by `dotnet ef migrations add` against SQL Server tooling not available in this
environment; the SQLite path used by every test here relies on `EnsureCreated`, exactly like BC-05/BC-09's own non-Docker test runs). A
`dotnet ef migrations add InitialCreate` against a reachable SQL Server should be run before a real deployment.

## Implemented
- **Domain** (11 files): `NewsArticle` (AGG-30) - `Draft -> Published -> Archived` state machine, idempotent double publish/archive (no
  second event), `CreateDraft`/`EditDraft` content-hash de-duplication (INV-01/02), media attach with size/format rules and alt-text-required-
  to-publish (INV-04/05), rule codes `HC.News.*` plus the handover's external codes (`E-NEWSU-*`). `ContentCategorization` (AGG-31, 1:1 per
  article) and its `ContentCategory` soft-deleted catalogue. `HelpContent` (AGG-33, covers FAQ/law/regulation/contract-type-regulation/guide/
  video/interactive-guide via `Kind` - Q-07) - atomic version-append on every `Update`, media attach with captions-or-text-alternative
  required (INV-09/10). `HelpContentOrganization` (AGG-32, 1:1 per article) and its `HelpTopic` soft-removed catalogue. `HelpFeedback`
  (AGG-34) - one-per-(user, article) upsert. Three **proposed** aggregates per handover section 3.6-3.8: `CompanyProfilePage` (owner-or-
  administrator edit of the page background BC-06 owns), `TutorialProgress` (`(UserId, TutorialId) -> CompletedAtUtc`), `ContextHelpMapping`
  (`PageKey -> HelpContentId`). `LocalizedText` value object (ar/en with same-aggregate fallback). All aggregates derive from
  `AggregateRoot<Guid>` and are sealed; no public setters (enforced by `ArchitectureTests`).
- **Application** (7 files): every command/query of handover section 7 and its FluentValidation validator; `HelpContentEventMapper`
  (domain -> the four frozen published integration events - `CompanyPageChangedDomainEvent` is internal-only, cache invalidation, and is
  never mapped); ports for BC-05 company info/standing, BC-09 open postings and BC-04 profile interests, each with an Http/Fake
  dual-provider selectable by configuration, exactly like BC-09's own `AddInternalApiClient` usage for BC-05/BC-08/BC-10.
- **Infrastructure** (9 files): EF Core `HelpContentDbContext` (schema `content`), owned-type mapping for every `LocalizedText`/media/
  version collection, JSON conversions for `ContentCategorization.CategoryIds/Tags` and `HelpContentOrganization.Roles`;
  `ContentCategorization`/`HelpContentOrganization`/`ContextHelpMapping` are deliberately mapped **without** a RowVersion concurrency token
  (`LastWriteWinsMapping.ConfigureAggregateLastWriteWins`) so the handover's "later save wins, no RowVersion rejection" (stories 3.7.1-04 AC-
  03, 3.7.2-02 AC-03) holds at the database level, not just in application logic; `HelpContentReadStore` (news/help lists, search, feed,
  help-center-by-role, feedback summary - see the portable-search deviation below); `LocalMediaStorage`, `HelpContentCache` (Redis-or-
  in-memory cache-aside for the composed company page, 5 min TTL); outbox wiring only (BC-06 **consumes** zero integration events per
  handover section 5.2, so there is no inbox).
- **Api** (6 files): every route of handover section 6.1 - `/api/v1/news...` (admin authoring + anonymous reads + job-seeker feed),
  `/api/v1/admin/content-categories`, `/api/v1/help...` (admin authoring + anonymous/role-filtered reads + feedback), `/api/v1/admin/help-
  topics`, `/api/v1/tutorials/{id}` (see deviation), `/api/v1/companies/{employerAccountId}/page` (anonymous) and `/api/v1/companies/me/
  page` (employer self-service) - implementing `GetCompanyProfilePageQuery`'s BC-05+BC-09-composed view. Role policies per route,
  `HelpContentErrorMessages` (ar+en, matching the shared catalog convention), ETag on `GET /news/{id}` and `GET /help/{id}`.

## Assumptions / deviations (handover section 12 open questions, and other decisions taken to keep moving)
- **Q-01 (10 MB media cap unrealistic for video)**: left as specified (10 MB applies to `NewsArticle` image attachments only; help
  video/interactive-guide media has no size cap enforced here since the handover names no number for it) - an external streaming host is
  out of scope for this pass and is not implemented.
- **Q-02 (`HelpContentUpdated` carries `fromStatus`/`toStatus` but help content has no status)**: both are populated with the constant
  `"Live"` (`HelpContent.LiveStatus`); the real signal is the added `fromVersion`/`toVersion` pair, matching the "proposed extra" the
  handover already names for this event.
- **Q-03 (news-feed personalisation rule)**: implemented as "match article categorisation tags against the job seeker's BC-04 profile
  interest tags" (`GetNewsFeedHandler`); falls back to the general feed when the job seeker has no interest tags, or when the personalised
  match set is empty.
- **Q-04 (nobody notifies users of new news)**: not implemented - `NewsArticlePublished` is published (BC-12 consumes it per the
  catalogue); no BC-13 consumer exists in this repo pass, consistent with the handover's own framing as a gap, not a BC-06 responsibility.
- **Q-05 (company page needs BC-09 open postings, flow absent from the context map)**: resolved. BC-09 (JobPlatform.JobPosting) already
  exposes `GET /internal/v1/employers/{id}/open-postings` (`ListOpenPostingsByEmployerQuery`, found while implementing this BC) -
  `IOpenPostingsProvider`'s Http adapter calls it and degrades to an empty list + `OpenPostingsDegraded=true` on failure (AC-04).
- **Q-06 (feed needs BC-04 profile interests, absent from the context map)**: proposed a new internal endpoint,
  `GET /internal/v1/profiles/{id}/interest-tags`, and implemented `IProfileInterestsProvider`'s Http adapter against it. BC-04 does not
  implement this endpoint in this repo pass (out of this BC's scope) - the Fake provider (always empty tags, fallback to general feed) is
  what every test here exercises, same as BC-05/BC-09's own not-yet-built dependencies.
- **Q-07 (are laws/regulations help content or a separate legal library?)**: same aggregate, distinguished by `HelpContent.Kind`
  (`Law`, `Regulation`, `ContractTypeRegulation` alongside `Faq`/`Guide`/`Video`/`InteractiveGuide`) - no separate aggregate.
- **D-01 (category/topic catalogues are soft-deleted reference tables, not separate aggregates)**: **not** followed as literally proposed -
  `ContentCategory` and `HelpTopic` are implemented as their own tiny `AggregateRoot<Guid>` types (own table, own repository) rather than
  value collections inside `ContentCategorization`/`HelpContentOrganization`, because admin manages the catalogue independently of any one
  article's assignment (`POST/DELETE /admin/content-categories`, `POST/DELETE /admin/help-topics`) and multiple articles reference the same
  category/topic row. The soft-delete behaviour itself (deleted/removed -> "uncategorized" fallback, never a broken reference) **is**
  implemented exactly as proposed, at the read-store layer (`HelpContentReadStore.ToListItem`/`TopicName`).
- **INV-06 (published article needs >= 1 category/tag "before appearing in categorised views")**: read literally as a *display* filter,
  not a publish guard - `NewsArticle.Publish` does **not** block on zero categories/tags (the handover cites no external error code for
  this case, and blocking publish on categorisation would contradict "Draft -> Published" needing only INV-03/05). An uncategorised
  published article appears in the general list/feed; `ListNews`'s category filter naturally excludes it, matching "categorised views"
  literally.
- **"Later save wins" (ContentCategorization, HelpContentOrganization, ContextHelpMapping)**: implemented as a genuine absence of an
  optimistic-concurrency token at the EF mapping level (see `LastWriteWinsMapping` in Infrastructure), not merely "the app never checks
  `If-Match`" - a real concurrent SaveChanges race from two loaded contexts was integration-tested (`PersistenceTests.
  ContentCategorization_ConcurrentOverwrites_LaterSaveWins_NoConcurrencyException`) and does not throw.
- **`GET /help/context?pageKey=`, unmapped key**: returns HTTP **204**, not the "200 with a null body" the handover's route table implies -
  ASP.NET Core's default `HttpNoContentOutputFormatter` converts any `Ok(null)` response into 204 automatically; fighting that convention
  (e.g. wrapping in `{ mapped: false }`) was judged not worth it since 204 already signals "nothing here, fall back" cleanly and no other
  BC in this repo works around the same framework behaviour.
- **`PUT /admin/help/context-mappings/{pageKey}`**: the route parameter is a **catch-all** (`{*pageKey}`), not a single segment - the
  handover's own examples (`"employer/dashboard"`) contain a `/`, which a normal route parameter cannot match.
- **`GET /tutorials/onboarding` (no id in the handover's literal route)**: implemented as `GET /api/v1/tutorials/{id}` and
  `POST /api/v1/tutorials/{id}/complete`. Tutorial content is `HelpContent(Kind=Guide)` and several tutorials can exist (e.g. one per
  audience/flow), so a single parameterless "the onboarding tutorial" route does not fit the domain model as specified elsewhere in the
  same handover section (3.7).
- **`POST /admin/help/{id}/media` without captions/text-alternative**: FluentValidation's `AttachHelpMediaValidator` catches this before
  the domain is reached, so the Api response is **400** `VAL.INVALID_REQUEST`, not the handover's **415** `E-FAQHC-UNSUPPORTED-FORMAT`.
  The domain invariant (INV-10) and its 415/`E-FAQHC-UNSUPPORTED-FORMAT` mapping still exist and are unit-tested directly
  (`HelpContentTests.AttachMedia_WithoutCaptionsOrTextAlternative_ThrowsNoCaptions`) - only the "first line of defence" changed layers, the
  same trade-off every BC in this repo makes between validator-layer 400s and domain-layer 4xx/409/422s for the same bad input.
- **`PUT /companies/me/page`**: wired for the `Employer` actor type only (a true "me" self-service route); the domain's
  `EditBackground` rule is owner-**or**-administrator per handover section 3.6 AC-04, but no separate admin-on-behalf-of route is named
  by the handover, so no admin-facing edit endpoint is exposed here (the domain rule stays broader for future admin tooling).
- **Full-text search (THR-013 <= 2s, Arabic+English full-text index)**: `HelpContentReadStore` uses a portable `EF.Functions.Like`
  keyword predicate (identical on SQL Server and SQLite) instead of the handover's SQL Server full-text catalogue, the same documented
  trade-off BC-09's `JobPostingSearchReadModel` already makes in this repo. Category/topic/tag filtering is resolved by loading the small
  `ContentCategorization`/`HelpContentOrganization` side-tables into memory rather than a SQL predicate against their JSON-converted
  columns - correct and simple at the seed volumes every test here uses, but not the design for a large catalogue (a normalised
  `ArticleCategories`/`ArticleTags` join table, as the handover's own data-model section 8 names, would be needed at scale).
- **Draft de-duplication (`UQ(ContentHash) WHERE Status='Draft')`**: enforced at the **application layer**
  (`INewsArticleRepository.GetDraftByContentHashAsync` before `CreateDraft`), not a DB-level filtered unique index, for the same reason
  BC-09 gives for its own identical-draft dedup: a plain unique index on `ContentHash` would also block two unrelated Published articles
  that happen to collide, and a *filtered* index needs provider-specific syntax EF cannot emit portably for both SQL Server and SQLite.
- Cross-BC providers (`HttpCompanyDirectoryProvider`, `HttpOpenPostingsProvider`, `HttpProfileInterestsProvider`) are wired against
  the `AddInternalApiClient` convention and (for BC-05/BC-09) the real route shapes read from those BCs' own controllers/handlers, but
  only their **Fake** counterparts were exercised here (no BC-05/BC-09/BC-04 instance was running in this environment) - the HTTP path
  compiles but is otherwise unverified end-to-end, exactly like BC-09's own not-yet-verified BC-05/BC-08/BC-10 Http adapters.

## Known limitations
- No load test: the help-search <= 2s and feed/help-center p95 <= 3s targets (THR-013) are not benchmarked here; see the full-text-search
  deviation above for the main functional gap versus that target.
- Category/topic/tag filtering loads the whole `ContentCategorizations`/`HelpContentOrganizations` table into memory per read (see
  deviation above) - fine at this repo's test/seed volumes, not the design for a large catalogue.
- The three cross-BC Http adapters (BC-05 company info, BC-09 open postings, BC-04 profile interests) are compiled but unverified against
  real running services (see deviation above); BC-04's proposed `interest-tags` endpoint does not exist anywhere in this repo pass.
- `POST /admin/news/{id}/media` and `POST /admin/help/{id}/media` store bytes to local disk (`LocalMediaStorage`, same pattern as BC-05's
  `LocalFileStorage`) rather than an external streaming host for video (Q-01) - no malware scanning is wired for either BC's media uploads
  in this pass (BC-05 explicitly documents a `PassthroughMalwareScanner`; BC-06 has no scanner port at all, since the handover names none).
- The solution-wide `dotnet build`/`dotnet test JobPlatform.sln` was **not** attempted, per this task's own instructions (sibling BCs are
  under concurrent development in this repository); every HelpContent project (`src` and `tests`) was built and tested individually and is
  green - see "Verified by running" above.
