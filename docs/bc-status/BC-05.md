# BC-05 Employer Onboarding - status

Complete (code + tests + migration). Dev port 5105. DB `JobPlatform_EmployerOnboarding`, schema `employer`.

## Implemented
- Domain: `EmployerRegistration` (Pending → Approved, INV-01..04, no reject path per source stories), `CompanyMediaAndDocument` (size/format/duplicate-by-hash/one-primary-logo, INV-05..08), `EmployerStanding` (admission + verification flags, idempotent/monotonic `MarkVerified`, `BadgeAuditEntry` for AC-04 traceability), `KnownAccount` replica.
- Application: commands/queries per handover §7 (`SubmitEmployerLevel2`, `ApproveEmployerRegistration`, `AttachCompanyMedia`, `RemoveCompanyMedia`, `SetPrimaryLogo`, standing/company queries), 2 inbox handlers (`AccountApproved` filtered to `ActorType.Employer`, `EmployerVerificationApproved` tolerant of arriving before the registration exists), domain-event mapper, `IFileStorage`/`IMalwareScanner`/`IEmployerCache` ports.
- Infrastructure: EF context (`employer` schema; `CompanyIdentity`/`Level2Details` stored as nullable JSON columns since they don't exist until submitted), repositories, read store, `LocalFileStorage` (disk under `FileStorage:RootPath`, default temp dir) + `PassthroughMalwareScanner` (no scanner wired in this environment), Redis-backed `IEmployerCache`, outbox/inbox wiring, initial migration.
- Api: `/api/v1/employers/me/registration/level2` (PUT/GET), `/api/v1/employers/me/media` (multipart POST/GET/DELETE/primary), `/api/v1/admin/employer-registrations` (list/approve), `/internal/v1/employers/{id}/standing` and `.../company` (service-to-service, implements the shape of `IEmployerOnboardingApi`).

## Decisions taken (handover §12 open questions)
- **Q-01** (company identity source): `AccountApproved` carries `actorType` only, no company identity fields. The employer supplies name/company-id/registration-number themselves in `SubmitEmployerLevel2Command` (Level-2 submission), not derived from the event. If BC-03 later enriches the event, this can be prefilled but the employer-supplied value is still authoritative for edits.
- **Q-04** (media formats): images = PNG/JPG, documents (`RegistrationDocument`) = PDF only; a registration-document upload with a non-PDF content type is rejected.
- **Q-06** (unapproved employer posting jobs): out of scope here by design — BC-05 only exposes the accurate `approved`/`verified` flags via `/internal/v1/employers/{id}/standing`; enforcing "approved employer may post" is BC-09's job when it exists.
- Size/format/primary-logo-kind violations are modeled as `BusinessRuleKind.BusinessRule` (422), not `InvalidInput` (400): they depend on domain state (the media `Kind`), not just the shape of the request.
- No `Reject`/return-for-changes path was added (Q-02) — the source stories don't have one; `EmployerRegistration` only ever moves Pending → Approved.
- `EmployerStanding` is modeled as a full aggregate root (not the "read model, not an aggregate" wording in the handover) so it can own its own optimistic concurrency and raise `EmployerStandingChangedDomainEvent` for cache invalidation; nothing about its public shape changed.

## Assumptions / deviations
- `CompanyIdentity`/`Level2Details` are stored as nullable JSON value-converter columns (not EF owned-entity navigations) to avoid EF Core's optional-owned-type materialization edge cases while keeping "not yet submitted" naturally representable as `null`.
- The composite (employer, file-hash) duplicate-upload uniqueness (INV-07) is enforced at the application level (`GetByHashAsync` before `Attach`) rather than a DB unique index, because the hash is a column of an owned sub-entity (`File.Sha256`) mapped into the same table; EF Core's dotted-path `HasIndex("EmployerAccountId", "File.Sha256")` syntax failed at model-build time in this EF Core version when the owned property had no declared CLR shadow type. This is a defense-in-depth gap, not a functional one — the domain check still prevents duplicates through the normal API path.
- `IFileStorage`/`IMalwareScanner` are local, dependency-free default adapters (disk + pass-through), matching the sibling BC-04 Job Seeker Profile build's approach; neither is shared code between the two BCs per the foundation's "nothing shared except SharedKernel" rule.
