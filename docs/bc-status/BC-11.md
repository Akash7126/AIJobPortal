# BC-11 Candidate Sourcing - status

Complete (code + tests + migration). Dev port 5111. DB `JobPlatform_CandidateSourcing`, schema `sourcing`.

## Implemented
- **Domain**: `CandidateProjection` (local, searchable replica of a candidate's BC-04-disclosed fields - not an aggregate root,
  rebuilt from BC-04's candidate-view API whenever `ProfileCreated`/`ProfileUpdated` arrive, since those events are near-id-only),
  `VerifiedEmployer` (local replica of BC-01's `EmployerVerificationApproved`, gates candidate-database search),
  `QualificationThreshold` (per-employer-per-posting cutoff, versioned), `CandidateInsight` (computed fit/availability/salary
  snapshot for one candidate against one posting, persisted so `CandidateInsightComputed` is published for BC-07/BC-12's audit
  trail), `TalentPoolEntry` (idempotent per employer/candidate/posting triple; `Create` refuses a candidate who is not currently
  visible to employers), `CandidateRankingService` (stable rank with lowest-id tie-break), `CandidatePrivacyPolicy` (a private
  candidate is excluded unless opted in; a deactivated candidate is always excluded). Error codes `E-CRFE-*` and rule codes
  `CS.<Area>.*`.
- **Application**: `Search` (verified-employers-only candidate-database search, GAP-001's proposed filter set - skills,
  education, experience, location, salary, availability; contradiction check on an inverted salary range), `Recommendations`
  (`CandidateQualificationService` shared by recommendations and ranking - loads the posting from BC-09, snapshots the effective
  threshold once per INV-06, filters BC-10's scored candidates by current privacy, caches the qualifying list per posting for 60s),
  `Insight` (pass-through fit computation against BC-10's match-score breakdown), `Threshold`, `TalentPool`. Five inbox handlers:
  `ProfileCreatedProjectionHandler`/`ProfileUpdatedProjectionHandler` (rebuild the projection from BC-04's candidate-view),
  `ExcludeCandidateHandler` (BC-03 `AccountSuspended` -> `MarkDeactivated`), `MarkEmployerVerifiedHandler` (BC-01
  `EmployerVerificationApproved`), `MarkPostingMatchesStaleHandler` (BC-10 `MatchScoreComputed` evicts the recommendations
  cache). `CandidateSourcingEventMapper` publishes 2 integration events (`TalentPoolEntryCreated`, `CandidateInsightComputed`) -
  deliberately thin, never carrying candidate PII. Dual-provider ports to BC-09 (`IJobPostingApi`), BC-04
  (`IJobSeekerProfileApi`) and BC-10 (`IAiMatchingApi`), each `Http | Fake` selectable by configuration.
- **Infrastructure**: EF Core `CandidateSourcingDbContext` (schema `sourcing`), repositories for every aggregate,
  `CandidateSourcingReadStore` (search + talent-pool listing, filtered to `!Deactivated && (Public || EmployerVisibilityOptIn)`),
  `CandidateSourcingCache` (cache-aside over the shared `ICacheStore`, Redis or in-memory), outbox/inbox wiring, internal-service-
  token HTTP client with retry-on-idempotent-GET for the three downstream clients, initial migration.
- **Api**: `CandidateSourcingControllerBase` (Employer role, `E-CRFE-FORBIDDEN`) with `ThresholdController`
  (`/api/v1/employers/me/jobs/{id}/qualification-threshold`), `RecommendationsController`
  (`.../candidate-recommendations`, `.../candidate-ranking`), `CandidatesController` (`.../candidates/search`,
  `.../candidates/{id}`, `.../candidates/{id}/insight`), `TalentPoolController` (`.../talent-pool`).

## Assumptions / deviations
- **GAP-001 (search filter contradictions)**: the only well-defined contradiction enforced is an inverted salary range
  (`salaryMin > salaryMax`); other filter combinations are accepted even if they yield no results.
- **Candidate-view is the single source of truth**: `GetCandidateViewHandler` always passes through to BC-04's own
  privacy-aware endpoint rather than re-deriving visibility from the local projection, per the handover's framing that BC-04
  owns what is currently disclosed.
- **`CandidateQualificationService` caching**: qualifying candidates per posting are cached for 60 seconds and evicted by
  `MarkPostingMatchesStaleHandler` on `MatchScoreComputed`; a cache miss recomputes from BC-10's `ListMatchScoresAsync` (page
  size 200) rather than paging through all scores.
- **`TalentPoolEntry.Create` visibility gate**: adding a candidate not currently visible to employers (no projection yet, or
  private/deactivated) is refused with `E-CRFE-FORBIDDEN` (`CS.TalentPool.NOT_VISIBLE`), matching US-3.3.3-07 AC-04 - a
  candidate must already have a `Public` (or opted-in) BC-04 profile projected here before an employer can save them.

## Verified by running
Domain 40, Application 34, Infrastructure 8, Api 26, Architecture (already present, unchanged) tests green; `dotnet build` of
all four `src` projects individually: 0 warnings, 0 errors.

**New in this pass**: `Api.IntegrationTests` (26 tests across `ThresholdApiTests`, `TalentPoolApiTests`, `CandidatesApiTests`,
`RecommendationsApiTests` - threshold set/get round-trip and range validation, talent-pool add/idempotent-add/remove/visibility
gate, verified-vs-unverified-employer search gating and filter round-trip, candidate-view visibility, insight ownership/
not-found/forbidden, recommendation empty-is-normal and qualifying-candidate inclusion, ranking order and tie-break) was
previously an empty skeleton and is now real and green.

**Fix needed to make the new tests pass (test-project-only, no production bug)**: `ApiFactory.Settings()` had to explicitly
override `JobPostingClient:Provider`, `JobSeekerProfileClient:Provider` and `AiMatchingClient:Provider` to `Fake` - the BC's own
`appsettings.json` defaults all three to `Http`, so without the override the test host tried to reach
`job-posting-api:8080`/etc. over real HTTP and every recommendation/insight/search call timed out after 2s and 500'd. The other
BCs' `ApiFactory`s (e.g. JobPosting's) already follow this same override pattern for their own Fake-provider settings; this BC's
skeleton had simply never been filled in before.

**Not executed here (no Docker / SQL Server / RabbitMQ / Redis)**: all Infrastructure/Api tests run against SQLite and the
in-memory cache/bus; the real RabbitMQ outbox/inbox publish/consume path, Redis cache and the real HTTP paths to BC-09/BC-04/
BC-10 are not verified against real servers.

## Known limitations
- Search is a local-projection filter query, not a full-text search; large candidate volumes are not benchmarked.
- The `HttpJobPostingApiClient`/`HttpJobSeekerProfileApiClient`/`HttpAiMatchingApiClient` code paths compile and follow the
  shared `InternalServiceTokenHandler`/retry convention but were only exercised here against their Fake counterparts (no
  BC-09/BC-04/BC-10 instance was running in this environment).
