# BC-09 Job Posting - status

Complete (code + tests + migration). Dev port 5109. DB `JobPlatform_JobPosting`, schema `jobs`.

## Implemented
- **Domain**: `JobPosting` aggregate (AGG-17 + AGG-21 merged per D-01) with the full lifecycle state machine
  (draft/active/paused/expired/archived), all invariants INV-01..08 with rule codes `JP.Posting.*` and the handover's external error codes
  (`E-JCP-*`, `E-JST-*`, plus two added codes - see deviations), value objects (`SalaryRange`, `ApplicationDeadline`, `JobLocation`,
  `JobVisibility`, `JobSource`, `SearchCriteria`, `InterestedReference`). `FavoriteJobList` (AGG-18, toggle semantics, no event on
  removal), `SavedSearch` (AGG-19, hash-based reuse, `EvaluateMatch` raising `SavedSearchMatched`), `InterestedListEntry` (AGG-20).
  `IJobPostingSchemaValidator` port + `ContentHasher` domain service.
- **Application**: all commands/queries/validators of handover section 7; `JobPostingEventMapper` (domain -> the 7 published integration
  events); 4 inbox handlers (`ImportExternalJobHandler` for `JobDataImported`, `SyncExternalPostingHandler` for
  `JobPostAttributionUpdated`, `ApplyAdminSuspensionHandler` for `JobOfferingSuspended`, `RefreshTaxonomyCacheHandler` for
  `PlatformTaxonomyUpdated`); `SavedSearchMatchEvaluator` (runs **inside** the same unit of work as every command that can make a
  posting Active, so `SavedSearchMatched` is captured by the outbox interceptor like any other domain event); ports for BC-08 taxonomy,
  BC-05 employer standing and BC-10 match ranking, each with an Http/Fake dual-provider selectable by configuration exactly like BC-08's
  `IUserDirectory`/`IReferenceUsageChecker`.
- **Infrastructure**: EF Core `JobPostingDbContext` (schema `jobs`, owned types for every value object, JSON conversions for
  lists/dictionaries), repositories, `JobPostingSearchReadModel` (see deviation below), Redis cache-aside for taxonomy/employer-standing
  (60 min / 5 min TTL), `ExpireDuePostingsJob` hosted service (auto-close, Redis leader lock, same pattern as BC-12's scheduled jobs),
  outbox/inbox wiring, initial migration.
- **Api**: every route of handover section 6.1 (`/api/v1/jobs...`, `/api/v1/favorites`, `/api/v1/saved-searches`, `/api/v1/interested`,
  `/api/v1/taxonomy/posting-schema`, and internal `/internal/v1/postings/{id}` implementing `IJobPostingApi`,
  `/internal/v1/postings/{id}/status-history`, `/internal/v1/employers/{id}/open-postings`,
  `/internal/v1/reference-usage/check` implementing the shared `ReferenceUsageCheckRequest/Response` contract), role policies per
  route, `JobPostingErrorMessages` (ar+en, test-enforced by the common catalog convention), ETag/If-Match, Idempotency-Key on
  `POST /jobs`, anonymous guest search/get.

## Assumptions / deviations (decisions taken to keep moving - handover section 12 open questions)
- **Q-02 (employer eligibility)**: decided **fail-open** - `EmployerEligibilityPolicy.MayPost` only blocks on an explicit "not approved"
  answer from BC-05; an unreachable/not-yet-built BC-05 does not block publishing, since BC-09 must stay usable standalone. The
  `EmployerStanding:Provider=Fake` adapter used in dev/tests always returns "no opinion" (null), so eligibility is never blocked
  locally.
- **Q-03 (targeted visibility)**: target audience = an explicit list of job-seeker ids (`TargetJobSeekerIds`); `GetJobPostingQuery`
  filters a `Private`/`Targeted` posting from anyone but the owner (or a listed job seeker).
- **Q-04 (import events)**: imported postings **do** publish `JobPostingCreated`/`JobPostingUpdated`, and are created directly in
  **Active** status (not Draft) since the external site already published them.
- **Q-05 (admin suspension)**: forces `Paused` + `AdminSuspended=true` (added error code `E-JST-ADMIN-SUSPENDED`, no external code was
  given for INV-06). No "lift suspension" flow exists in the event catalogue for either BC-08 or BC-09, so once suspended a posting
  stays refused for Resume/Renew/Publish until BC-08 gains that capability (tracked as a gap, not implemented here).
- **Q-06 (saved-search match ownership)**: implemented as proposed - BC-09 emits `SavedSearchMatched` via `SavedSearchMatchEvaluator`,
  run synchronously whenever a posting transitions to (or is created directly in) Active.
- **Q-09 (open-ended fields)**: `OtherFields` (`IReadOnlyDictionary<string,string>`, max 20 keys, validator-enforced).
- Added error code `E-JST-INVALID-TRANSITION` for a status change outside the documented transition table (neither archived-terminal
  nor renew-only-when-expired, which keep their own codes).
- **INV-03 (identical-draft dedup)** and the import upsert-by-`PlatformJobId` are enforced at the **application layer** (repository
  lookup before `Add`), not by a database unique constraint: a content-hash collision across non-draft statuses must not block
  unrelated postings, and a DB-level filtered unique index would need provider-specific syntax (SQL Server vs SQLite) for no real
  extra safety here. A concurrent double-submit race is closed by the ordinary `RowVersion` optimistic-concurrency check on the
  loaded/found draft, not by a unique index.
- **`/internal/v1/postings/{id}/status-history`** returns an empty list. BC-07 Audit Logging already consumes
  `JobPostingStatusUpdated` and holds the authoritative audited history (handover's own framing: "local trace" vs BC-07's audit
  trail); BC-09 keeps no separate `jobs.StatusChanges` table for this backfill-only endpoint.
- **`/internal/v1/reference-usage/check`**: BC-09 answers for reference types `skills` (checked against posting `Skills`), `jobs`
  (checked against `CategoryCode`) and `trainings` (checked against `RequiredTraining`); `datasets` is not owned by this BC and always
  reports "not in use".
- **Search / full-text (THR-013 <= 2s at 50k postings)**: the read model uses a portable `EF.Functions.Like` keyword predicate that
  runs identically on SQL Server and SQLite, so the service works out of the box on both without a SQL Server full-text catalogue.
  This **does not** meet the sub-2-second-at-scale target on its own - a production deployment should add a SQL Server full-text index
  on Title/Summary (Arabic 1025 + English 1033, handover T-04) and switch the predicate to `CONTAINS`. Not implemented here (never
  benchmarked at 50k rows; no SQL Server available in this environment - see Known limitations).
- **Guest Action Gate (US-4.1-03)**: protected endpoints return the platform-standard `401 E-AAFR-UNAUTHORIZED` (via the shared JWT
  challenge) rather than the handover's bespoke `401 code=E-UI-FORBIDDEN, registrationRequired=true` shape. Implementing a
  per-endpoint custom challenge body was judged not worth the complexity versus the standard convention every other BC already
  uses; the UI can still show a "please register" prompt off the plain 401.
- **ETag on mutations**: `POST /jobs`, `PUT /jobs/{id}` and `POST /jobs/{id}/renew` do **not** return an `ETag` header on their own
  response. A `RowVersion`/rowversion token is only assigned when `SaveChanges` runs, which happens *after* the handler returns
  inside the same command pipeline (foundation section 6) - a value captured in the handler's result would be the stale pre-save
  array, not the true new tag (this mirrors why BC-03/BC-08 only ever set `ETag` from GET/query responses, never from a mutation's
  own result). `GET /jobs/{id}` always returns a fresh, correct `ETag` usable as `If-Match` on the next `PUT`.
- **Later-save-wins** (`PUT /jobs/{id}`, handover section 3.1): a caller that omits `If-Match` accepts that its save may replace a
  concurrent edit; the response's `overwritten` flag is `true` whenever `If-Match` was omitted (a caller that supplies `If-Match`
  already gets a `412 E-PRECONDITION-FAILED` above on a stale read, so it never reaches this flag).
- Employer eligibility, taxonomy and match-ranking adapters (`Http*Provider`) are wired against the real published contracts in
  `SharedKernel.ApiContracts.{PlatformAdministration,EmployerOnboarding,AiMatching}`, but were only exercised here against their
  **Fake** counterparts (no BC-08/05/10 instance was running in this environment); the HTTP path compiles and follows the
  `AddInternalApiClient` convention used elsewhere but is otherwise unverified end-to-end.

## Verified by running
Domain 39, Application 18, Infrastructure 5, Api 9, Architecture 16 tests green (87 total); `dotnet build` of all four `src`
projects individually: 0 warnings, 0 errors; API smoke-run in Development (SQLite + in-memory cache/bus): `/health/live`,
`/health/ready`, `/api/v1/jobs/search` all responded correctly.

**Not executed here (no Docker / SQL Server / RabbitMQ / Redis):** no `[DockerFact]`-tagged tests were written for this BC (all
Infrastructure tests run against SQLite, consistent with BC-03/BC-07's Docker-optional pattern) - the SQL Server-specific paths
(schemas, real `rowversion`, full-text search) and the real RabbitMQ outbox/inbox publish/consume path are therefore **not**
verified against real servers, only against their SQLite/in-memory equivalents.

## Known limitations
- No load test: search latency and the 500-postings/day / 50,000-active-postings throughput targets (THR-013/020/027) are not
  benchmarked here.
- The full-text search deviation above (portable `LIKE` instead of SQL Server `CONTAINS`) is the main functional gap versus the
  handover's performance target.
- PII/location columns are not encrypted at the application level (consistent with BC-03's documented approach: left to SQL Server
  TDE / Always Encrypted configuration).
- The solution-wide `dotnet build JobPlatform.sln` was **not** achieved during this work: at the time of writing, sibling bounded
  contexts under active, concurrent development in this repository (`EmployerOnboarding.Application`, `CandidateSourcing.Application`,
  and a `AiMatching.Domain.UnitTests` file referencing members that do not exist on `MatchScoringEngine`) fail to compile for reasons
  unrelated to and untouched by this BC-09 work. Every JobPosting project (`src` and `tests`) was built and tested individually and is
  green; see the "Verified by running" section above. Those other BCs' compile errors should be fixed by whoever owns that work.
