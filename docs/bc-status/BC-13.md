# BC-13 Notification - status

Complete (code + tests + migration). Dev port 5113. DB `JobPlatform_Notification`, schema `notify`.

## Implemented

Notification delivers e-mail, in-app (SignalR) and SMS to users of every other BC, driven by a small number of inbound integration events and two
service-to-service use cases (transactional OTP/password-reset SMS for BC-03, a masked-detail backfill for BC-07).

- **Domain** (7 files): three sealed `AggregateRoot<Guid>` types with their own lifecycle - `InAppNotification` (Unread/Read/Deleted, recipient-only
  mutation, raises `InAppNotificationCreatedDomainEvent`/`InAppNotificationStatusChangedDomainEvent`), `OutboundMessage` (Pending/Sending/Sent/Failed/
  Suppressed/Digested, bounded retry with exponential backoff and a max of 3 attempts, one-time-code bodies cleared once sent/failed, raises
  `OutboundMessageSentDomainEvent`), `JobConfirmation` (source-platform+source-job to platform-job-id mapping, exactly-once, raises
  `JobConfirmationSentDomainEvent`). Five plain `Entity<T>` configuration/preference types deliberately *not* modelled as aggregates (last-write-wins, no
  optimistic-concurrency token): `NotificationPreference` (per-account channel/category settings, JSON-backed dictionaries, one-click unsubscribe),
  `EmailTemplate` (versioned, `{{placeholder}}` rendering with per-placeholder defaults, administrator-only edits always create a new version),
  `NotificationType` (icon/colour/text-alternative catalogue with a WCAG-AA contrast check, `Contrast.OnWhite`), `SmsPolicy` (versioned essential-category
  list - OTP and password-reset can never be removed), `WeeklyCycle` (one weekly recommendation per account per ISO week). Domain services: `ChannelRouter`
  (preference/consent/suspension/essential-SMS routing, including re-routing a non-essential SMS to e-mail+in-app), `ComplianceGuard` (anti-spam sender-
  domain and unsubscribe-link checks, SMS sender-id/segment/prohibited-content checks), `DedupeKeyFactory` (idempotent composition keys).
- **Application** (9 files): `NotificationComposer` (the single write path for both channels - routes, renders, applies compliance, and idempotently
  composes `OutboundMessage`/`InAppNotification` rows so a redelivered source event never yields a second message, INV-06), `OutboundDispatcher` (drives a
  composed message through provider send), `NotificationEventMapper` (domain events to the three published integration events, recipients always masked,
  bodies never published). Five inbox handlers reacting to other BCs' events (`SavedSearchMatchedIntegrationEvent`, `JobRecommendationComputedIntegrationEvent`
  with the weekly-cycle dedupe, `JobDataImportedIntegrationEvent` for job-confirmation callbacks, `AccountApprovedIntegrationEvent` for the welcome message,
  `AccountSuspendedIntegrationEvent` to suspend further sends). User-facing use cases: the notification center (`InApp/InApp.cs` - list/read/delete/take-
  action, always scoped to the caller), preferences (`Preferences/Preferences.cs` - per-channel get/set plus the anonymous signed-token one-click
  unsubscribe), delivery (`Delivery/Commands.cs` - start/complete/fail-send worker steps, the signed provider delivery-report webhook command, the
  service-to-service transactional-SMS command, the service-to-service notification-detail query), digest (`Delivery/Digest.cs`), admin configuration
  (`Admin/Admin.cs` - e-mail templates, notification types, essential SMS categories, paged SMS delivery status).
- **Infrastructure** (12 files): EF Core `NotificationDbContext` with the one initial migration already applied, JSON-backed value converters for
  `NotificationPreference`'s three private-field collections and `EmailTemplate.Placeholders`, unique indexes matching every domain invariant
  (`OutboundMessages.DedupeKey`, `EmailTemplates`(code,version,locale), `JobConfirmations`(sourcePlatformId,sourceJobId), `WeeklyCycle`(accountId,isoWeek)),
  eight aggregate-oriented repositories, `NotificationReadStore` (paged read models for the notification center and SMS deliveries), `NotificationSeeder`
  (idempotent: essential-SMS policy v1, six built-in notification types, the `welcome` and `job-confirmation` e-mail templates), `HmacUnsubscribeTokens` and
  `HmacWebhookVerifier` (both HMAC-SHA256, configurable signing keys), `FakeProviders`/`HttpContactApi` adapters (deterministic fake e-mail/SMS/contact
  providers selected by `Contacts:Provider` configuration, a real HTTP adapter to BC-03's contact endpoint as the drop-in replacement), `SignalRNotifier` +
  `ConnectionTracker` + `NotificationHub` (real-time in-app push at `/hubs/notifications`, offline users simply keep the notification Unread), a
  `DispatcherService` hosted service (polls due `OutboundMessage`s and drives them through the provider) and a `DigestService` hosted service (batches
  digest-mode e-mail).
- **Api** (5 files): `/api/v1/notifications` (the caller's own notification center), `/api/v1/notification-preferences` (own channel settings),
  `/api/v1/unsubscribe/{token}` (anonymous one-click), `/api/v1/admin/...` (administrator-only template/type/SMS-policy configuration and delivery status),
  `/api/v1/webhooks/{sms-delivery|email-events}` (anonymous but HMAC-signed provider callbacks, `X-Signature` header), `/internal/v1/notifications/...`
  (service-to-service, `Policies.InternalService` - client-credentials token with the internal scope, transactional OTP send and notification detail).

## Assumptions / deviations
- **`NotificationPreference`/`EmailTemplate`/`NotificationType`/`SmsPolicy`/`WeeklyCycle` are plain entities, not aggregate roots**: the domain code
  comments are explicit that these are "last-write-wins" with no optimistic-concurrency token by design (AC-04 in `NotificationPreference`'s doc comment) -
  this is a deliberate simplicity trade-off for settings/config data, not an oversight, so the architecture tests assert exactly three aggregate roots
  (`InAppNotification`, `OutboundMessage`, `JobConfirmation`), not eight.
- **`ChannelDecision`/`ChannelRouter` re-routing**: a non-essential-category SMS is never sent - it is silently re-routed to e-mail and in-app instead of
  being refused outright, so a caller requesting SMS for a non-essential category still gets a notification through another channel.
- **Mandatory categories cannot be disabled** (`SecurityAlert`, `Otp`, `PasswordReset`): `NotificationPreference.SetEmailPreference`/`SetInAppPreference`
  throw a `BusinessRuleViolationException` (mapped to `422 Unprocessable Entity`, `BusinessRuleKind.BusinessRule`) if a caller tries to turn one off.
- **`Contacts:Provider` defaults to the Fake adapter** in `appsettings.Development.json` (no explicit setting there), consistent with every other
  BC-to-BC Http/Fake dual-provider convention in this repository.

## Known limitations
- No Docker / SQL Server / RabbitMQ / Redis in this environment: all new tests run against SQLite and the in-memory cache/bus, consistent with every other
  BC's Docker-optional pattern. The real RabbitMQ outbox/inbox publish/consume path and the real SMTP/SMS-gateway/BC-03-contact HTTP adapters are not
  verified against real servers here (only their Fake counterparts).
- SignalR real-time push (`NotificationHub`/`SignalRNotifier`/`ConnectionTracker`) was not exercised by the new tests - hub connection testing would need a
  `TestServer`-backed SignalR client, judged out of scope for this pass given the REST surface already gives solid coverage of the notification-center and
  compliance/routing logic that the hub merely re-broadcasts.
- The `DispatcherService`/`DigestService` hosted-service polling loops themselves were not exercised end-to-end (the API tests disable them via
  `Notification:DispatcherEnabled`/`DigestEnabled = false` to keep tests deterministic); their underlying `OutboundDispatcher`/digest logic is covered by
  the pre-existing `Application.UnitTests`.
