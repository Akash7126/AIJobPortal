# BC-12 Reporting - status

Complete (code + tests). Dev port 5112. DB `JobPlatform_Reporting`, schemas `reporting` (analytics store) and `config` (report configuration).

## Implemented

Reporting is a read-model / projection bounded context: it owns no lifecycle aggregates of its own domain (no "posting", "account", etc.); instead it
ingests ~45 integration events published by the other twelve BCs, turns them into a denormalised analytics store, and serves reports, dashboards, a
Power BI OData feed, exports, schedules and access control over that store.

- **Domain** (10 files): a **fact/read-model layer** (`FactEvent`, `FactJobPosting`, `FactSkillDemand`, `FactMatch`, `FactRegistration`, `FactNotification`,
  `FactSystemMetric`, `FactOutcome`, `AggDaily`) written directly by ingestion (no aggregate invariants - `Facts.cs`), plus a genuine
  **report-configuration domain** with ten sealed `AggregateRoot<Guid>` types: `ActivityLogRetentionPolicy` (singleton, legal-minimum-guarded retention),
  `ReportTemplate` (versioned parameter schema, later-save-wins), `ReportSchedule` (own five-field cron parser `CronExpression`, Daily/Weekly/Monthly/Cron
  intervals, raises `ReportDistributionRequestedDomainEvent`), `SavedReport` (owner-only report library, 12-month retention), `ReportExport` +
  `ReportExportFile` (Queued/Generating/Ready/Failed lifecycle, idempotent by parameter hash), `ReportAccessRule` + `ReportAccessDecision` (role-to-category
  RBAC plus an audited decision that raises `ReportAccessDecidedDomainEvent`), `PerformanceAlertRule` + `PerformanceAlert` (threshold rules over five known
  system metrics, raises `PerformanceAlertRaisedDomainEvent`), `LaborMarketReport` (one per calendar month). A `ReportDefinition`/`ReportCatalog` value-object
  layer whitelists which fields/aggregations/filters each of the three data sources (Activity, Employment, Performance) exposes to the ad-hoc report builder.
- **Application** (24 files): `EventIngestionService` + a generic `IngestionHandler<TEvent>` (one inbox consumer per catalogued event type, deduped by
  `MessageId`) driving per-event-type **projectors** (`PostingProjectors.cs`, `OtherProjectors.cs`) that update the fact tables and the `AggDaily` rollups;
  `EventCatalog` maps every one of the 45 consumed events (from BC-01, 02, 03, 04, 05, 06, 08, 09, 10, 11, 13, 14 - i.e. every other BC) to an activity type,
  actor and subject, asserted complete by `EventCatalogTests`. Four report "modules" per the handover: Module A user-activity monitoring (`Activity.cs`,
  admin-only, pseudonymous actor keys via SHA-256), Module B employment statistics (`Employment.cs`, `LaborMarket.cs` - trends, industries, skills, geography,
  salaries, outcomes, all insufficient-data/small-cell-suppression aware via `StatisticsPolicy`), Module C system performance (`Performance.cs` - matching
  metrics, technical metrics, alert rules, usage patterns, dashboards), Module D custom/ad-hoc reports (`ReportEngine.cs`, `ReportRunner.cs`, `ReportRuns.cs`,
  `ReportLibrary.cs`, `ReportMapping.cs`, `ReportFiles.cs`, `ExportContent.cs`, `Exports.cs`, `Schedules.cs`, `ODataFeed.cs` - report builder, template/saved-
  report CRUD, render/run to table or chart view, CSV/Excel/PDF export generation, cron-based scheduling with e-mail distribution via BC-13, the read-only
  OData feed for Power BI service principals, and per-category `ReportAccessGuard`/`IReportAccessGuard` RBAC that also produces the audited access-decision
  trail for BC-07).
- **Infrastructure** (9 files): EF Core `ReportingDbContext` (two schemas, JSON-backed collections, unique indexes matching every domain invariant -
  `FactEvent.MessageId`, `FactSkillDemand`(skill,side,subject), `AggDaily`(day,metric), `ReportExports`(requestedBy,parametersHash) filtered to
  Queued/Generating, `ReportAccessRules.Role`, `LaborMarketReports.Period`), `FactStore` (write side, change-tracker-aware `GetOrOpen*` helpers so a unit of
  work never double-inserts), `AnalyticsQueryService` (read side, `AsNoTracking` projections straight to row records, never through aggregates), ten
  aggregate-oriented repositories, three pluggable external-system adapters each with a Fake/Http (or Simulated/Prometheus/None) pair selected by
  configuration (`IMetricsSource`, `ISessionSource`, `IPowerBiExporter`), `ReportingJobs` (six leader-locked/cache-locked scheduled jobs: export
  generation, schedule runs, metric sampling, alert evaluation, retention, labor-market generation), outbox (publishes `PerformanceAlertRaised` and
  `ReportDistributionRequested` to BC-13, and the access-decision as a BC-07 `AuditRecord`) and inbox wiring for all 45 consumed events.
- **Api** (5 files): `/api/v1/admin/reports/...` (activity, employment, labor-market, system, custom/templates/schedules/exports/saved/access-rules, all
  `[Authorize]` + `Administrator`+MFA enforced per-request via `CategoryRequest`/`IAuthorizedRequest`, not by an MVC policy), `/odata/v1` and `/odata/v1/{view}`
  (service-principal-only, `ActorType.System`), `/api/v1/reports/shared/{id}` (anonymous, HMAC-signed expiring download link for scheduled distributions).

## Assumptions / deviations
- **Read-model BC, no domain aggregates of its own business lifecycle**: unlike a typical BC, `Fact*` rows are written directly by the ingestion pipeline,
  not through aggregate behaviour methods - this is intentional (see the class doc comments in `Facts.cs`) since the analytics store's job is to mirror
  other BCs' published state, not to enforce invariants of its own. Reporting's genuine aggregates are its ten report-configuration types instead.
- **`ReportAccessGuard` default-allow for administrators**: when none of the caller's roles (plus the implicit `"Administrator"` key every administrator
  carries) has a configured `ReportAccessRule`, the guard defaults to allow (GAP-002 in the domain doc comments) - i.e. every MFA-verified administrator can
  use every report category until an administrator explicitly restricts a role.
- **OData feed is read-only and service-principal scoped**: the service document itself (`GET /odata/v1`) only requires authentication (any actor type can
  see the list of views), but the per-view query (`GET /odata/v1/{view}`) is gated to `ActorType.System` - administrators get the report endpoints instead.

## Known limitations
- No Docker / SQL Server / RabbitMQ / Redis in this environment: all new tests run against SQLite (via `SqliteTestDatabase<TContext>`) and the in-memory
  cache/bus (via `ApiTestFactory<Program>`), consistent with every other BC's Docker-optional pattern in this repository. The SQL-Server-specific paths
  (columnstore indexes / monthly partitioning mentioned in `FactConfigurations.cs`, the real RabbitMQ outbox/inbox publish/consume path) are not verified
  against real servers here.
- SignalR/real-time and the actual HTTP adapters (`HttpSessionSource`, `HttpPowerBiExporter`) were not exercised (Simulated/Fake providers were used
  throughout, matching the `appsettings.Development.json` defaults); only the Fake-provider code paths are covered by these new tests.
