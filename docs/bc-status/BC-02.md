Complete (code + tests + migration). Dev port 5102. DB `JobPlatform_ExternalIntegration`, schema `extint`.

  `JobDataMapping` (AGG-25, merges the partner-configured "Data Mapping" US-3.1.3-04 and the sync-time "standardisation" US-3.4.1-03 per handover

  config), `SoftwareInterfaceConnection` (proposed AGG, admin-only idempotent registry), `ApiSchemaAccessLog` (records + raises
  `ApiSchemaDocumentationViewed` on every schema-doc view). Plus two plain replica entities (`KnownPartnerAccount`, `PartnerCredential`, mirroring
  BC-05's `KnownAccount` pattern) fed by inbox handlers. All invariants INV-01..10 implemented as `BusinessRule`s with the handover's rule codes
  (`EI.Aggregate.RULE`) and external error codes (`E-EJSI-*`, `E-TPJPRI-*`, `E-APIF-*`, `E-SI-*`, plus codes added by this implementation where the
  handover named a rule without an external code - see deviations). Value objects: `SourcePlatform`, `SyncModels`, `SyncSchedule`, `StandardJob`,
  `MappingRule`.
- **Application**: `RegisterExternalJobSiteCommand`, `ApproveExternalJobSiteCommand`, `ActivateIntegrationCommand`, `SuspendIntegrationCommand`
  (proposed), `EnableIntegrationCommand`, `ConfigureSyncScheduleCommand`, `ConfigureAttributionVisibilityCommand`, `ProvisionSandboxCommand`,
  `StartSyncRunCommand`, `PushJobDataCommand`, `SyncJobPostAttributionCommand`, `ConfigureJobDataMappingCommand`, `ReleaseApiVersionCommand`,
  `DeprecateApiVersionCommand`, `RetireApiVersionCommand`, `ConfigureApiDataFormatCommand`, `RegisterSoftwareInterfaceCommand`,
  `ViewApiSchemaDocumentationCommand` (see deviation) + matching queries (`GetIntegrationQuery`, `GetIntegrationSummaryQuery` for BC-07/BC-09,
  `GetJobDataMappingQuery`, `GetStandardSchemaQuery`, `GetApiDocumentationQuery`, `GetSoftwareInterfaceDocumentationQuery`, `ListApiVersionsQuery`)
  and validators per handover section 7.3. `PartnerSyncOrchestrator` (handover 4.2 application service): pull → Receive → Standardize → Accept per
  job, independent partial failure, upstream-timeout mapped to 502. `ExternalIntegrationEventMapper` (domain → the 6 frozen published integration
  events). Two inbox handlers: `RegisterKnownPartnerAccountHandler` (BC-03 `AccountApproved`, ExternalJobSite actor - handover's proposed
  `RegisterPartnerAccountHandler`, renamed for clarity) and `RecordPartnerCredentialHandler` (BC-03 `ApiCredentialCreated`).
- **Infrastructure**: EF Core `ExternalIntegrationDbContext` (schema `extint`, owned types for `SourcePlatform`/`SyncModels`/`SyncSchedule`/

- **Api**: partner surface (`api/v1/partner/...`: integration registration/get, enable models, sync schedule, attribution visibility, sandbox,

## Assumptions / deviations (decisions taken to keep moving - handover section 12 open questions)
- **Q-05 / BC-09 payload-thinness risk - verified, no mismatch found**: the task flagged a risk that BC-02's catalogued `JobDataImported` payload
  might be thinner than what BC-09's `ImportExternalJobHandler` actually needs. Inspection of the **frozen, already-published** contract in
  `SharedKernel/IntegrationEvents/ExternalIntegration/ExternalIntegrationEvents.cs` shows it is **already the enriched shape** the handover asked
  for (Q-05): `platformJobId`, `sourceJobId`, full standardised job fields (title/summary/skills/contractType/workFormat/deadline/location/
  sourceUrl), `attributionVisibility`, `isUpdate`, `aggregateVersion`. Reading `src/Services/JobPosting/JobPlatform.JobPosting.Application/
  Events.cs` confirms `ImportExternalJobHandler` and `SyncExternalPostingHandler` consume exactly these fields (e.g. `e.PlatformJobId`,
  `e.AttributionVisibility`, `e.DeadlineUtc`) with no thinner/ids-only version anywhere. **No action was needed or taken on the event shape** -
  this BC-02 implementation simply had to (and does) raise `JobDataImportedDomainEvent`/`JobPostAttributionUpdatedDomainEvent` with every field
  the mapper needs to populate the frozen record, which it does (see `Application/Events.cs`'s `ExternalIntegrationEventMapper`).
- **Q-06 (job id assignment)**: implemented as the handover assumed - `JobData.Accept` issues `PlatformJobId` (a new GUID string) on first
  accept and reuses it on every later accept for the same source key; BC-09 reuses it verbatim as its own aggregate key entry point
  (`JobSource.FromExternal(..., e.PlatformJobId, ...)`).
- **Q-04 (recommended-sites source)**: not integrated with a BC-08/Platform-Administration reference file (out of scope, not built anywhere yet
  in this repo) - `RegisterExternalJobSiteCommand` simply carries a `recommendedByMolPef` flag supplied by the caller at registration time,
  exactly as the handover's fallback option describes ("flag at registration").
- **Q-01 (pull/push wording)**: implemented as documented - pull = platform fetches via `IPartnerJobFeedClient`; push = partner posts to
  `POST /partner/jobs`. True platform→partner export is out of scope here, per the handover's own resolution.
- **Q-02 / Q-03 (docs access split, and publishing `ApiSchemaDocumentationViewed`)**: implemented exactly as the handover's own resolution -
  `GET /partner/schema-documentation` requires an active partner credential and publishes the view event on every call; `GET /docs/{version}`
  is anonymous and never publishes anything.
- **D-01 / D-02**: implemented exactly as proposed - `JobDataMapping` is one aggregate for both stories; the four handover 4.4 infrastructure
  stories (TLS, communication-interface catalogue, hardware topology, client baseline) are **not** modelled as aggregates or endpoints in this
  pass - they are operational/IaC concerns outside a single BC's application code (tracked below as a known limitation, matching the handover's
  own framing that they are "infrastructure/operations controls, not application code").
- **`ViewApiSchemaDocumentationQuery` modelled as a command**: viewing the schema has a side effect (it logs the view and must publish
  `ApiSchemaDocumentationViewed` atomically with that log row). The shared CQRS pipeline only runs the unit-of-work/outbox commit for
  `ICommandBase` requests, not for `IQuery`, so `ViewApiSchemaDocumentationCommand` is deliberately an `ICommand` behind a `GET` route (the HTTP
  verb reflects the caller's intent; the CQRS marker reflects what the pipeline must do). This mirrors no existing BC pattern exactly but keeps
  every side effect inside the same transactional/outbox machinery every other write in this codebase uses, rather than open-coding a
  bespoke save path only for this one query.
- **Cron validation**: no cron-parsing library dependency was added. `ConfigureSyncScheduleValidator` checks five space-separated fields and
  that the minute field is not `*` (and, if `*/N`, that `N >= 5`) to approximate the ">= 5 minute interval" AC (3.4.1-05 AC-02). A fixed-minute
  cron (e.g. `0 * * * *`, hourly) is accepted without deeper semantic validation.
- **`PlatformJobId` uniqueness** (among non-null values) and the **"one running sync per integration"** invariant are enforced at the
  **application/domain level** (repository lookup before `Add`, and `ExternalJobSiteIntegration.StartSyncRun`'s in-aggregate check against its
  loaded `SyncRuns` collection) rather than by a DB constraint - a provider-portable filtered unique index needs different syntax on SQL Server
  vs SQLite for no real extra safety here (mirrors BC-09's documented INV-03 decision). `(SourcePlatformId, SourceJobId)` **is** a true DB-level
  unique index since both columns are always non-null.
- **No real partner HTTP client**: `IPartnerJobFeedClient`'s only adapter is `FakePartnerJobFeedClient`, which always returns an empty page (no
  Docker/network egress available in this environment - see Known limitations). The anti-corruption-layer port and the `PartnerSyncOrchestrator`
  application service (Receive → Standardize → Accept per job, independent partial failure, `PartnerUpstreamTimeoutException` → 502
  `E-EJSI-UPSTREAM-TIMEOUT`) are fully implemented and unit-tested against a configurable fake (including a simulated timeout that leaves the
  `SyncRun` persisted as `Failed`); a production deployment adds an `HttpPartnerJobFeedClient` (Polly: 30s timeout, 3 retries with jitter) behind
  the same port with no Application-layer change.
- **No Redis caching layer** was implemented for BC-02 (handover section 9: credential-controls, api-versions list, docs, rate-limit counters).
  All reads go straight to the database; this is a known limitation, not a design decision - the read volumes in this exercise don't need it to
  demonstrate correctness, and every other cross-cutting concern (outbox, inbox, idempotency, rate limiting via the shared pipeline) is wired.
- **Software-interface catalogue** (`SoftwareInterfaceConnection`, US-4.3-01) only exercises the `ExternalJobSite`/`EmailSmsGateway`/
  `GovernmentDatabase`/`AnalyticsReporting` categories as an admin-managed registry; it does not call out to BC-01's
  `GET /internal/v1/government-systems` to auto-populate government entries (handover 6.2 "degrade: omit with warning") - entries are
  registered manually via `PUT /admin/software-interfaces`.
- **Added error codes** (handover named the rule but gave no external code): `E-EJSI-RUN-IN-PROGRESS`, `E-EJSI-NOT-ACTIVE`,
  `E-EJSI-ALREADY-REGISTERED`, `E-APIF-ADMIN-ONLY`, `E-APIF-RETIRE-BEFORE-SUNSET`, `E-APIF-INVALID-TRANSITION`, `E-SI-FORBIDDEN`,
  `E-EI-NOT-FOUND` (mirrors BC-05's `E-EO-NOT-FOUND` convention).
- **`PUT /partner/mapping` and `PUT /admin/api-versions/{v}/format` return 400** (not 422) for their respective "required field unmapped" /
  "unsupported format" refusals - this matches the handover's own API table literally (`400 E-TPJPRI-REQUIRED-FIELD`), which classifies these as
  malformed-input rather than business-rule refusals; implemented via `BusinessRuleKind.InvalidInput`.

## Known limitations
- **No real partner HTTP integration**: see the "No real partner HTTP client" deviation above. Pull-model syncs always see an empty feed in
  this environment; the push model (`POST /partner/jobs`) is the fully exercised, real end-to-end path.
- **No Redis caching** for credential-controls/api-versions/docs/rate-limit counters (handover section 9) - reads always hit the database.
- **US-4.2-01/02, US-4.4-01/02 (hardware interfaces, client-device baseline, communication-interface catalogue, TLS 1.3/OAuth2 enforcement)**
  are not implemented as application code, consistent with the handover's own framing of them as infrastructure/operations controls (IaC,
  ingress/Kestrel config) rather than BC application logic; no `GET /api/v1/platform/client-baseline` endpoint or communication-interface
  catalogue endpoint was built. A future pass could add a thin static-config endpoint for these if a consumer needs one at runtime.
- **Credential validation model (Q-07)**: `PartnerCredential.IsActive` is a plain expiry check (`ExpiresAtUtc > now`) against the local BC-03
  replica; there is no IP-whitelist/usage-limit enforcement or Redis-cached "controls" call (`IApiCredentialControlsApi`) as the handover's
  §6.2 "Consumed APIs" row describes - only the existence of an active credential is checked, which is sufficient for every invariant this BC
  itself owns (sandbox provisioning, schema-doc viewing).
- **BC-01 government-systems integration** for the software-interface catalogue is not called (see deviation above) - government entries are
  registered manually rather than synced.
- The solution-wide `dotnet build`/`dotnet test JobPlatform.sln` was **not** attempted, per this session's explicit constraint (other bounded
  contexts are under concurrent development in this repository). Every ExternalIntegration project (`src` and `tests`) was built and tested
  individually and is green; see "Verified by running" above.
