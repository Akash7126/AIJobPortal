# BC-04 Job Seeker Profile - status

Complete (code + tests + migration). Dev port 5104. DB `JobPlatform_JobSeekerProfile`, schema `profile`.

## Implemented
- **Domain**: `Profile` aggregate (owner-account 1:1, Level1/education/experience/skills/training/certificates/level3 sections,
  completion-percent computation, `ApplyExtractedData`/`ApplyReviewedSkills` merges from BC-10's resume parsing, `Deactivate`),
  `Resume` (one current resume per profile, upload supersedes never duplicates), `SupplementaryDocument` (owner is either a
  job-seeker profile or, for US-3.1.2-08, a company - shared aggregate with a `DocumentOwnerType` discriminator), `ProfileShareLink`
  (token generation gated on `PrivacySetting.PublicSharingActive`), `PrivacySetting` (visibility, deactivation/deletion request
  state), `JobPreference` (job types/industries/locations/salary/work-arrangement, last-write-wins, no `RowVersion`), `KnownAccount`
  (inbox-fed replica of BC-03 standing) and `ProcessedParsedData` (idempotency guard for BC-10 merges). Value objects `FullName`,
  `Email`, `MobileNumber`, `Gender`, `SkillKind`/`SkillClass`, `WorkArrangement`. Error codes `E-JSRPM-*` (+ `E-ERPM-*` for the
  company-document owner type) and rule codes `JP.<Aggregate>.*`.
- **Application**: every command/query of the handover (`Profile`, `Documents`, `Resume`, `ShareLink`, `Privacy`, `Preferences`,
  `Internal`), FluentValidation validators for every mutating command, `JobSeekerProfileEventMapper` (domain -> the 3 published
  integration events `ProfileCreated`/`ProfileUpdated`/`ResumeCreated`), 5 inbox handlers (`RecordKnownAccountHandler` for
  `AccountApproved`, `DeactivateProfileHandler` for `AccountSuspended`, `ApplyExtractedProfileDataHandler` for
  `ResumeParsedDataComputed`, `ApplyReviewedDataHandler` for `ParsedProfileDataUpdated`, `RefreshTaxonomyCacheHandler` for
  `PlatformTaxonomyUpdated` - a no-op stub, see limitations), ports `IFileStorage`/`IMalwareScanner`/`IQrCodeRenderer`/
  `IAccountIdentityClient`/`IProfileReadStore`. `If-Match`/optimistic-concurrency enforced by `ProfileCommandSupport.LoadOwnedAsync`
  (reject-on-conflict, unlike `JobPreference`'s deliberate last-write-wins).
- **Infrastructure**: EF Core `JobSeekerProfileDbContext` (schema `profile`, JSON conversions for list-valued properties, owned
  types for value objects), repositories for every aggregate, `ProfileReadStore`, outbox/inbox wiring, initial migration.
  Adapters: `LocalFileStorage` (filesystem, `FileStorage:LocalPath`, the only storage provider shipped), `NoOpMalwareScanner`
  (always reports clean - no AV engine wired), `PlaceholderQrCodeRenderer` (bordered SVG frame with the URL as text, **not** a
  scannable QR matrix), `FakeAccountIdentityClient`/`HttpAccountIdentityClient` dual-provider to BC-03
  (`AccountIdentity:Provider = Http | Fake`).
- **Api**: `ProfileController` (`/api/v1/profiles...`, JobSeeker role), `DocumentsController` (+ `CompanyDocumentsController` for
  US-3.1.2-08 employer documents, Employer role), `ShareLinkController` + anonymous `SharedProfileController`
  (`/shared/{token}`, `/shared/{token}/qr`), `InternalController` (`/internal/v1/profiles/{id}`,
  `/internal/v1/profiles/{id}/privacy`, `/internal/v1/profiles/{id}/candidate-view`, `/internal/v1/resumes/{id}/content-url` -
  implements the shared `IJobSeekerProfileApi` contract consumed by BC-10/BC-11), ETag/If-Match on the profile, role policies per
  route, `JobSeekerProfileErrorMessages` (ar+en).

## Assumptions / deviations
- **File storage provider**: only `Local` (filesystem) is shipped; `FileStorage:Provider` has no `S3`/Azure Blob adapter in this
  pass.
- **Malware scanning**: `NoOpMalwareScanner` always reports clean - no antivirus engine is wired (an open question in the
  handover).
- **QR rendering**: `PlaceholderQrCodeRenderer` returns a bordered SVG frame with the share URL as visible text, not a real
  scannable QR matrix. A follow-up should swap in a real encoder (e.g. QRCoder).
- **Taxonomy cache**: `RefreshTaxonomyCacheHandler` is a no-op - no local BC-08 taxonomy cache is populated in this build; the
  consumer binding exists so the queue/routing is real, but the cache-eviction body is a small follow-up.
- **Out-of-order resume-parsing merges**: `ApplyExtractedProfileDataHandler`/`ApplyReviewedDataHandler` throw when the profile
  has not landed yet, relying on the inbox processor's retry to eventually succeed once `ProfileCreated` is durable.

## Verified by running
Domain 26, Application 15, Infrastructure 5, Api 42, Architecture 11 tests green (99 total); `dotnet build` of all four `src`
projects individually: 0 warnings, 0 errors.

**New in this pass**: `Api.IntegrationTests` (42 tests across `ProfileApiTests`, `DocumentsApiTests`, `ShareLinkApiTests`,
`InternalApiTests` - happy paths, validation 400s, not-found 404s, ownership/actor-type 403s, ETag/If-Match 409 conflicts,
multipart document/resume upload, anonymous share-link read) and `ArchitectureTests` (11 tests - layer dependency rules, handler
naming, aggregate-root sealing, domain-event/integration-event shape, frozen integration-event contract snapshot) were both
previously empty skeletons and are now real and green.

**Production bug found and fixed by these tests**: `JobPreferenceConfiguration` (`Persistence/Configurations.cs`) converted the
`JobTypes`/`Industries`/`Locations`/`WorkArrangements` JSON columns back into `string[]`/`WorkArrangement[]` on read, but the
domain's backing fields are `List<string>`/`List<WorkArrangement>` and the property is mapped with
`PropertyAccessMode.Field` (EF sets the backing field directly via reflection). Materializing a `JobPreference` row therefore
threw `InvalidCastException: Unable to cast object of type 'System.String[]' to type
'System.Collections.Generic.List\`1[System.String]'` on every read (`GET /api/v1/profiles/me/job-preference` after any
`PUT`), a 500 for every caller. Fixed by deserializing into `List<T>` instead of `T[]` so the runtime type matches the field.
This is provider-independent (would reproduce on SQL Server too, not a SQLite-only artifact) and was never caught before because
no existing test round-tripped a `JobPreference` through the database.

**Not executed here (no Docker / SQL Server / RabbitMQ / Redis)**: all Infrastructure/Api tests run against SQLite and the
in-memory cache/bus; the real RabbitMQ outbox/inbox publish/consume path and SQL Server-specific behavior are not verified
against real servers.

## Known limitations
- File storage, malware scanning and QR rendering are all placeholder/local-only implementations (see deviations above) - none
  are production-ready as shipped.
- No BC-08 taxonomy cache is actually populated by `RefreshTaxonomyCacheHandler`.
- PII fields are not encrypted at the application level (left to SQL Server TDE / Always Encrypted configuration, consistent
  with other BCs).
